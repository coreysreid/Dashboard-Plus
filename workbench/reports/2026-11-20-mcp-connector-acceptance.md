# Shipped MCP connector: acceptance run

Checked **20 November 2026** against `workbench/drafts/agent_api/MCP_ACCEPTANCE.md`, the shipped `src/dashboard/connector/`, Settings → Helpers, `tests/test_mcp_connector.py` and `tests/test_helper_api.py`. All people, items and key values used by the tests were invented and confined to temporary data. No key is printed here. This is a connector and local Dashboard run, **not** a test with a named AI assistant app or model.

## Worst first

1. **Client key storage unverified (check 4, partial).** Dashboard says the assistant app keeps the copied settings in a file and the key is a password. No named MCP client was installed for this run, so we cannot say where that client saves the key, whether other computer accounts can read it or whether removing the `dashboard-plus` entry removes all copies. Before publishing a named-client guide, test its exact save, permission and removal path. The connector itself reads environment values or an explicitly named TOML file; it does not store the key.
2. **Untrusted text is labelled, but model behavior is unverified (check 11, partial).** The connector returned the invented hostile item name as household data and made only the requested records call. No AI model was in this run, so “no extra external request” cannot be guaranteed for an arbitrary assistant. The real boundary is the connector's eight-tool allowlist, key grant and person-only Review.
3. **Oversized API response needs a forced integration probe (check 9, partial).** `client._read` stops after `MAX_ANSWER + 1` bytes (4 MiB cap) and returns a plain `too_large` error; the 41-test run covers oversized incoming MCP messages, timeout, redirects and ignored proxy settings, but not a real API response exceeding 4 MiB. Add a deliberately oversized authenticated local response in a connector test before calling this case fully exercised.

The original checklist has two outdated expectations, **not connector failures**: check 2 permits both `127.0.0.1` and `localhost` in the shipped URL validator (decision 0083); check 4's “next call returns 401” is normally a `not_dashboard`/old-address-or-key-off message **before the key is sent**, because a revoked key cannot pass the identity proof (0086). A 401 is possible only if revocation happens between proof and the actual request. Its Pets weigh-in example in check 7 was tested with an invented demo item instead; the staged-then-Review rule is the same.

## Reproduction and results

From the repository root, run `PYTHONPATH=src /tmp/dashboard-plus-venv/bin/python -m unittest discover -s tests -p test_mcp_connector.py -q`. On 20 November: **41 tests, OK** in 12.4 seconds. Those tests start an actual local Dashboard web server with a temporary module, records and helper keys. `KeySafetyTests.test_the_entry_point_runs_as_a_program` launches `python -m dashboard.connector` as a subprocess. I also ran `/tmp/lane_b_mcp_live_probe.py` (a disposable script, not committed) against the same live fixture: the process exited 0, wrote seven parseable JSON reply lines for seven requests, offered exactly eight expected tools, omitted the synthetic key and private value from stdout/stderr, kept the proposal waiting while the live record count stayed 3, returned the same batch on the same retry and `request_key_reused` on a changed retry.

The setup text should be checked with at least one real desktop MCP client, and an end-to-end assistant run should treat a hostile record as data. The original checklist remains useful as a design record; use the corrected behavior in this report for current acceptance.
