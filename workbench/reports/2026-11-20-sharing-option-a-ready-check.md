# Shared-folder option A: readiness check after Corey's sync choice

Checked **20 November 2026** against `docs/plans/household-sharing.md` option A, decisions 0081 and 0089, the shipped backup/restore and helper-key behavior, [SQLite's network-filesystem guidance](https://www.sqlite.org/useovernet.html) and [Syncthing's syncing/conflict guide](https://docs.syncthing.net/users/syncing.html). The official pages were reachable and read on this date. This is a **read-only fallback review, not a request to build A**: Corey chose main/member push–pull sync in decision 0089, and decision 0081 now says it is superseded. A would need a new product decision before implementation.

## Not ready, worst first

1. **The whole shared database conflicts with the chosen privacy boundary.** Option A puts `household.db` into a shared folder, including access instructions, Home layout codes and vehicle registration. Decision 0089 says those fields stay on the copy where they were typed; medical safety notes are a specified exception that may travel. OneDrive/Dropbox would also hold an unencrypted copy on a provider's servers under the old proposal. Encrypting the whole file would protect it from the provider but still give the member all fields after opening; filtering fields would require a record-level exchange and merge design close to chosen sync. **Decision needed:** retire A, or define a distinct privacy contract and get Corey's explicit approval. Do not imply it is a privacy-equivalent fallback.
2. **A cloud folder is not a cross-computer lock or compare-and-swap.** The proposed 15-minute `lease.json` renewals and `household.json` generation are copied asynchronously. Two offline computers can each see a free or stale lease and the same generation, both pass their local check, and each write. Syncthing documents that simultaneously changed files can be renamed as conflict copies; which becomes the global file is chosen by modification time or device ID, not by Dashboard's generation. Size/hash and SQLite integrity checks catch partial or damaged arrivals, but do not make the check-in comparison atomic between devices. **Decision needed:** whether A is explicitly “take turns with manual conflict recovery,” or a real single-writer guarantee is required. The latter needs a coordinating authority, not only files mirrored by a cloud service.
3. **The proposed conflict recovery is not built.** The plan says set-aside copies can be opened on Review to copy changes across. Today Review handles new helper/import rows, not a before/after diff between two SQLite databases, updates, deletes or Stock movements. Restore preview shows counts, not the changed rows. A household could keep both files without knowing which records differ. **Decision needed:** a row-level reconciliation tool, or clear manual export/compare instructions and a promise limited to “both copies kept,” never “nothing was lost.”
4. **Read-only and restore need a full write gate.** If another device owns the turn, hiding save buttons is insufficient: every page POST, local helper API proposal/Accept, import, one-step action, backup restore/Undo, background job and safe close/check-in must obey the same mode and generation rule. A restore after another computer has checked in could overwrite newer shared work unless it pauses sharing and sets its copy aside. **Decision needed:** which operations are allowed in look-only mode and what a restored copy may publish.
5. **Key and version behavior is unspecified.** Helper fingerprints live outside the database and backups. A copied `core__helpers` row does not bring its key to the other computer, and a turned-off key must not revive when an older shared copy arrives. App/module migration versions must be checked before opening a copy; a newer writer must not hand an older binary a database it cannot use. **Decision needed:** local helper rows and keys on checkout, device/person audit attribution, compatible-version policy, and recovery when an older device returns.

The plan's source-memory claims about OneDrive and Dropbox conflict-file names, retention and lease-file arrival times are **unverified** here. Do not make household instructions depend on a particular filename or delay. Syncthing's official guide confirms a `.sync-conflict-…` pattern, but its policy and filesystem behavior still need a two-computer trial. SQLite's official warning is about database I/O over network filesystems; option A wisely keeps live SQLite local, yet the asynchronous file-copy race above remains a separate issue.

## Acceptance checks if Corey ever reselects A

| # | Two invented devices and action | Required result before build is called ready |
|---|---|---|
| 1 | Fresh install, sharing off; open Settings and every normal page. | Badge and footer truthfully say local only; no shared file is written. Turning A on is an explicit choice with the full-file privacy warning. |
| 2 | Try to share with access codes and registration values present. | The page explains exactly which fields and provider can receive them; A cannot be enabled under 0089's v1 rule without an approved exclusion/encryption design and a new decision. |
| 3 | Start two devices offline from the same generation; edit different Stock items; reconnect in opposite orders. | Neither side is silently overwritten. Both complete copies are retained with identities and checksums; a person can inspect **row-level** differences before choosing. |
| 4 | One device holds the lease; use forms, helper API, Review Accept, import, one-step actions and Restore on the other. | Every write path refuses with one clear look-only message. Read-only is enforced in core, not merely by hidden buttons. |
| 5 | Let the lease expire because a device sleeps; take over; wake it and attempt check-in. | Both versions remain, the newer generation is not overwritten, and the waking device gets a concrete recovery path. Repeat with skewed clocks and delayed cloud delivery. |
| 6 | Interrupt copying `household.db` before `household.json`, then the reverse; present a wrong hash or failed integrity check. | Neither partial or unmatched copy is opened or published. Existing local records stay usable. |
| 7 | Have Syncthing make a conflict copy, including delete-versus-edit; use a provider with a different conflict filename. | Discover every relevant extra copy without assuming one vendor's naming convention; do not auto-delete or auto-merge it. |
| 8 | Restore/Undo on one device while another holds a newer generation. | Sharing pauses, restores remain local, and a deliberate reconciliation is required before any shared check-in. |
| 9 | Turn a helper key off on one device, then check out an older shared DB on both. | Fingerprint stays removed; no restored row revives it. A helper made on one device is not falsely shown as connected on another. |
| 10 | Upgrade one device's app/module schema, leave the other old; try both check-in directions. | Incompatible copy is refused with upgrade words, the old data remains intact, and no migration runs inside the shared folder. |
| 11 | Stop sharing or move the shared folder. | The local copy remains usable and backed up; page names the remote copies that still exist and never promises remote deletion. |

The chosen main/member design in `workbench/drafts/sync/` addresses changes as records rather than copying a whole database. Option A should remain an unselected comparison unless Corey asks to revisit it.
