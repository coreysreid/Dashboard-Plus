# Windows beyond the portable zip

Batch 24 item 129. Planned **27 November 2026**. The current Windows release path is an unsigned, unzip-and-click folder from a successful GitHub Actions run. It carries Python, the app and a `data` folder beside them, and can run from a USB stick. CI tests its launch, local-only host check and safe close. This plan describes an **additional installed version**, not a replacement for the household's portable copy or proof that an installer exists.

## What a household would do

1. Choose **Install on this Windows computer** or **Keep the portable USB version** on the download page. The installed choice opens a trusted Microsoft Store listing if the MSIX path below passes its prototype and Store review. The portable choice still has the current manual unzip and update steps, with an honest warning that it is unsigned today.
2. Install from the Store, open **Dashboard Plus** from Start and see the same local browser dashboard. The installed app says where its records are kept; installing the program does not import a portable household automatically. It never asks for a bank login, password, code, full card or ID copy (decision 0141).
3. If moving an existing portable household, choose **Bring records from a portable copy**. Pick that copy's folder, see its household name and last checked backup, then make and verify a fresh Dashboard backup and restore into the installed app's own data folder. The original USB copy stays untouched. The screen says **These are now separate copies. New changes in one will not appear in the other unless household sharing is set up later.** An occupied installed folder is never overwritten by a guess.
4. **Start when I sign in** is an opt-in choice, off by default. It states that Dashboard will be available on this computer and that a later paired main computer may become reachable to members while signed in. The app shows how to turn it off both here and in Windows Startup settings. Starting at login must not silently expand sharing permissions.
5. Store updates replace program files; records and checked backups remain. The app makes a verified backup before a schema migration on next launch, says when an update needs a restart, and refuses a too-new data folder if an older app is opened. **Save and exit** still closes it and reports the backup result. If an update or migration fails, the household sees a recovery path using its checked backup, not a vague reinstall instruction.

The Store route should remove the specific **Unblock the zip** step from the installed-version journey. The portable path keeps a clearly scoped help page for downloads from the project's own release page; it should never tell someone to turn off Windows protection globally or unblock an unknown file.

## Which route first

| Route | Signing and warning | Updates and cost | Fit for Dashboard |
|---|---|---|---|
| **Microsoft Store MSIX — first installed prototype** | Microsoft re-signs the submitted package. Store installs are not subject to SmartScreen download warnings. Store approval and real-machine installation must still be tested. | Store-managed delivery; Microsoft's new developer-account onboarding currently has no registration fee, but requires account/identity verification. Build and support time remain. | Best household path if bundled Python, local server, helper connector, data location and backups work in an MSIX. Test all before committing. |
| Store listing for a traditional MSI/EXE | Publisher must sign the installer and hosted executable files with a trusted certificate; Microsoft Store can list it. | Publisher hosts the installer and owns updates. Certificate, hosting and updater work add costs. | Fallback if MSIX cannot preserve the app's local behavior; Store presence alone does not provide Store-managed MSI/EXE updates. |
| Direct signed MSI/EXE or MSIX download | A trusted signature names the publisher, but a new signed file can **still** show SmartScreen until its file or publisher gains reputation. An EV certificate no longer guarantees an instant pass. | Certificate and hosting costs, plus either a reviewed updater or a manual update. Direct MSIX can use a signed `.appinstaller` feed. | Useful when the Store route is unsuitable, but do not promise a warning-free first download. |
| Existing portable zip | Unsigned batch launchers, no installer and no Store requirement. It keeps `data` beside the app for a USB workflow. | Free to distribute; the household manages updates, backing up and safe USB removal. Windows may warn, and its online-file mark can require a deliberate Unblock after source verification. | Keep as an explicit portable option. Do not turn its data folder into an installed app's data folder by copying program files around it. |

**Recommendation:** prototype the Store MSIX route first while retaining the portable zip. If the package cannot pass the local-server, backup, helper and migration checks, document the exact failure and compare a signed installer. Do not buy a certificate or promise a warning-free direct installer before the route is proven. Microsoft's current new Store onboarding is free for individual and company accounts, but an individual Store publisher uses their own name; User 1 must choose the public publisher identity and complete Microsoft's verification outside this repository. Company enrollment has different proof requirements. No account, identity document or signing key belongs in Dashboard records, a PR or CI logs.

## Build order for Lane A

| Step | Core and release work | Gate |
|---|---|---|
| 1. Preserve today's portable route | Keep its zip, made-up smoke test, checked backup and honest Windows warning help. Publish a versioned download rather than telling households to pick an arbitrary green CI artifact. | Real Windows 10/11 test of a downloaded zip, including the exact Unblock problem User 1 saw. Verify the source and checksum before any Unblock instruction. |
| 2. Separate program and installed data | Package the bundled Python, app and modules as read-only program files. Give the installed version a per-user data folder outside the package, with owner-only permissions, and a distinct second-backup location. Define how `--data`, portable mode, helper address and multiple local Windows accounts behave. | No code or database writes in the signed package; no portable data silently moved, overwritten or shared. A second copy in the same folder or disk is not a computer-loss backup. |
| 3. Make an installable launcher | A Start-menu entry opens one local server and browser page, with one data-folder owner, a failure message and Save and exit. Replace batch files in the installed path; keep batch files only in the portable path. | Install, launch, close, reopen and uninstall on clean Windows 10/11 accounts without a developer Python or administrator rights where the chosen package permits. |
| 4. Prove the MSIX path | Build an MSIX from pinned, checked components; use a test package for functionality, then Store signing and certification for release. Verify package identity, data location, helper connector, loopback listener, generated guide and backup/restore in the **installed** artifact. | A Store install on a clean real Windows computer opens without the portable zip's Unblock step. Store denial or runtime breakage sends this back to the route decision. |
| 5. Opt-in sign-in start | Offer the choice only after a working installed launch. For MSIX, declare a packaged desktop startup task disabled by default; let the user enable/disable it and respect Windows Startup controls. Avoid opening a browser tab every login unless chosen. | Start once per sign-in, stop cleanly, no background process after opt-out, no automatic pairing or sharing. Test a crash, locked session and two Windows accounts. |
| 6. Updates and recovery | Use Store MSIX delivery if chosen; version the package and make a checked Dashboard backup before any data migration. For direct distribution, separately design signed update authenticity, complete program replacement, retry and rollback. | Interrupted update, full disk, a newer database, failed migration and a restored old backup all have a clear safe outcome. No update overwrites `data` or unsent member changes. |

An installed version is not the same as a sync main computer that starts on login. Pairing and transport still wait for the independent remote-boundary review and decisions 0089/0140. The installer must not expose the local server beyond loopback as a shortcut to phone access.

## The zip warning, accurately

The current README tells a tester to right-click the downloaded ZIP and choose **Unblock** before extraction. Microsoft's `Unblock-File` documentation says this removes the `Zone.Identifier` mark that Windows put on a downloaded file. It removes a warning signal; it does **not** verify that the zip came from the project or make an unsigned program signed. For the portable path, first show the exact release source, checksum and filename, then explain the local Unblock choice only for that verified file. On a managed computer the organization may still prohibit running it; do not suggest bypassing that rule. For the Store MSIX path, the household does not do this step.

Signing also needs exact wording. Microsoft says a new non-Store binary can still trigger SmartScreen with a valid certificate. Paying more for an EV certificate solely to skip the first warning no longer works. The plan must not promise **no warning** on a direct download; the clean Store MSIX route is the first candidate for a trusted install.

## Checks before saying it is ready

1. On clean Windows 10 and 11, install from the intended Store listing, not a developer sideload. Launch, close, reopen, uninstall and reinstall under two ordinary user accounts; confirm records remain private to the right account and uninstall words never imply data was erased if it remains.
2. Move an invented portable household by checked backup and restore. Verify records, dates, example sharing choices, last-four fields, retired sensitive fields, helper keys' separate handling and the two backup locations. Cancel halfway and try a second occupied destination: neither copy changes unexpectedly.
3. Start at sign-in off, opt in, sign out/in, then turn it off in both Dashboard and Windows Settings. Ensure one server, the correct account/data folder and no automatic browser flood or sharing choice change.
4. Install a newer Store version with the app open, with the app stopped and with a deliberately interrupted download. Check backup-before-migration, accepted record IDs, a refused too-new database on old code, and recovery after migration failure. Test manual/direct update separately if offered.
5. Test the helper connector, local API permission boundary, loopback binding, host/launch-token refusal, Save and exit, reports and data-folder ACLs in the packaged app. A package container or file virtualization must not put records in the program files or lose them on update.
6. Download the portable release zip in Edge, verify source/checksum, extract on NTFS and a USB stick, and record whether Windows marks the batch files. Check the exact Unblock words and that no step disables SmartScreen or changes a global security setting. Confirm closing before USB removal and manual program update without replacing `data`.
7. If a non-Store installer is offered, test a first download on a fresh Windows machine: show the real publisher and any SmartScreen prompt exactly as seen, verify signature and update authenticity, and do not claim that signing alone guarantees no warning.
