# Stage 0: independent security review brief for household sync

Prepared **20 November 2026** for batch 17 item 71. This is a brief for a reviewer who did not design or build the sync boundary. Decision 0089 accepts one main, offline members, private-network pull and push to Review. Decision 0055 currently treats Dashboard as local-only. **No remote listener or sync API is shipped.** The reviewer should assess the proposed protocol and implementation plan now, then verify the implemented boundary and repeat attack tests before stage 2 (pairing and pull) is released. No code change or self-attested checklist substitutes for that independent review.

## Reviewer's scope and evidence

Review the trust crossing from a Tailscale or self-run WireGuard peer into the main process, from main into a member's local database, and from a member's outbox into main's Review. Include both network adapters, adapter switching, invitation and member-key lifecycle, TLS identity pinning, snapshot/delta format, portable change log, local-only field filtering, backup/restore epochs, module migrations, and later USB format where the same exchange serializer is reused. Assume an attacker can join the private network, control a paired member, replay or modify traffic, send malformed records and cause network loss at any byte. Assume a stolen member key or laptop separately. The private network is one gate, not proof of a Dashboard identity.

The implementer should give the reviewer: protocol specification and state diagram; route and listener inventory; trust-boundary diagram; field-travel classification for every shipped column; sample filtered snapshot, delta, outbox and Review request using invented data; key storage and rotation design; maximum payload/page sizes; failure and recovery state table; test harness for two isolated copies; and a clean build on two computers. Secrets used in testing must be disposable and excluded from reports. The reviewer gets source and a reproducible build, can inspect dependencies and run negative tests, and may ask for a second build after fixes.

## Highest-risk questions and attack tests

| Priority | Boundary to review | Test idea and required result |
|---|---|---|
| Critical | Listener exposure | With sharing off, restart, sleep/wake, network removal and restore: scan loopback, LAN, Wi-Fi, public and VPN interfaces. Sync listener exists only on the selected private address while explicitly on. Wildcard, public and router-forwarded routes fail closed. Helper and browser routes remain loopback-only, including `/api/v1/`, `/review`, `/settings/backups`, `/settings/export` and settings. A direct request to a private address cannot reach those local routes. |
| Critical | Local-only fields crossing | Put unique invented sentinels into `people.important_info.detail` for `kind=access`, all Home layout `access_details` columns and `vehicles.registration` on both copies. Search raw network capture, portable log/outbox, Review staging, errors, debug logs, crash reports, temporary files, USB bundle before encryption and post-import data. No value, substring, hash, length or search token crosses. A missing marker never clears a local value. Medical allergy, condition, medication, care_need and dietary details *do* travel, behind Show and on the emergency sheet; `kind=other` defaults local. Test a medical→access kind change with an already-synced value as a special blocking transition. |
| Critical | Pairing and main identity | Substitute an attacker process at the expected IP, change DNS/private address or certificate, replay an invitation, pair two devices with one invitation, and try a helper key as a member key. No member secret or records leave before main identity is verified and pinned. Invitation is short-lived and single-use; member and helper key namespaces cannot authorize each other's routes. No bearer key in URL, QR shown to bystanders, report or log. |
| Critical | Authorization and route confusion | From a paired member, call local page, helper, restore, export, Review accept/reject and admin endpoints through the sync listener. All are refused before any side effect. Try malformed Host, Origin, method, path encoding, request content type, redirects and a nested proxy. Sync credentials authorize only the named device and allowed sync operations. A member cannot approve its own push. |
| High | Snapshot integrity and cursor | Truncate, reorder, duplicate and tamper with pages; change household ID, schema version, global links, digest, epoch and cursor; interrupt during apply. Old member copy remains usable until a fully verified atomic apply. Cursor advances only with applied rows. No partial or cross-household import; a gap causes a new checked snapshot, retaining the member's unsent outbox. |
| High | Replay, race and resource limits | Send the same operation ID with identical and changed bodies; parallel requests near caps; oversized and deeply nested payloads; many unknown IDs; slow connection and repeated bad proofs. Identical retry returns the prior result, changed-body reuse fails, work is bounded, rate limits are atomic, no SQLite lock starvation or secret-bearing error. Test clock skew; clocks never decide identity or conflict. |
| High | Restore, revocation and rollback | Revoke a member, restore an older main backup, Undo restore, restart, then replay an old key, cursor and push. Revocation survives backup rollback; restore advances epoch and pauses exchange. An old snapshot cannot resurrect deleted rows or erase new ones. Lost member keeps its existing data, so UI never promises remote erasure. |
| High | Module and record isolation | Feed malicious global IDs, cross-module links, disabled/older module rows, HTML and instruction-like text. Revalidate schema, links and module versions under the final write lock. Preserve decision 0055's migration confinement; no remote input becomes SQL, template code or a module file. Review renders untrusted text as text and never applies a row until the person accepts it. |
| High | Network adapter swap | Pair over WireGuard, switch to Tailscale, and reverse. Change private address mid-request and inject a public address. Listener closes and rebinds only after validating selected private interface. Main identity is rechecked at the new endpoint, member key and cursor remain scoped to the same household, and provider keys/names do not enter sync records. A third adapter must meet the same contract. |
| Medium | Data at rest on member | Inspect local database, backups, temp files, OS key store and permissions after pull and after revocation. State honestly what the member keeps; device encryption and physical loss are residual risks. Medical safety data travels intentionally; local-only details remain on their origin. No automatic deletion of existing copies is promised. |

## Specific design review prompts

1. Draw the authentication sequence, including TLS certificate/public-key pinning, fresh nonces, proof binding to main identity and one-use invitation. Check replay windows, key rotation, stolen-key response and whether any unauthenticated reply reveals a household or module name. The helper `/api/v1/hello` pattern is a precedent, not a sync protocol to copy verbatim.
2. Trace every output from a changed private field: snapshot, delta, outbox, portable audit entry, Review row, conflict text, notification count, log, error and future USB bundle. Conditional `people.important_info.detail` needs a fail-closed kind check. Check free-text fields that users may misuse to store secrets; this is a product wording and residual-risk finding, not a claim that filtering can understand arbitrary text.
3. Check one authoritative main, atomic revision assignment, duplicate request decisions, tombstone retention, linked-row dependency ordering and the exact point at which a member sees accepted versus merely staged work. Review should require a human for every incoming row under 0089.
4. Inspect bind and firewall behavior on both initial network providers. Validate what happens on interface changes, DNS rebinding, tunnel loss, process crash, restart and simultaneous local UI use. No shared Flask app or permissive route prefix should expose local routes remotely by accident.
5. Review recovery from backup restore, member retirement, long-offline return and a rejected push. A new snapshot must not discard the member's outbox or clear origin-only details. Check what survives keys kept outside backups.
6. Assess dependencies and cryptography separately before stage 5's USB bundles. A private network and TLS do not replace authenticated bundle encryption; Python's standard library has no suitable AEAD here.

## Report and release gate

Return a ranked report with **critical, high, medium, low** findings. Each finding needs a reproducible invented-data test, affected trust boundary, impact, exact precondition, proposed fix and retest result. State what was reviewed by source, by runnable build, or remains unverified. Record the build commit, OS, network adapter versions and test date. Keep test keys and traces out of the public repository; redact paths and identifiers. A finding that exposes a local-only value, enables unauthorised read/write, bypasses human Review, opens a public/wildcard listener, or permits rollback/replay of revoked identity blocks stage 2. Resolve and independently retest all critical and high findings before stage 2 ships; assign an owner and follow-up for remaining findings. Re-run the boundary review when push/Review (stage 3), conflicts (stage 4), USB (stage 5) or a phone client changes the attack surface.
