# Household sync: a proposed design, not a shipped feature

Updated **20 November 2026** for accepted decision 0089, after checking the shipped People, Home layout and Vehicles field definitions. This is a design, not a shipped feature. All people, devices and records in examples are invented.

## What a household would do

The first computer is **main**: it owns the accepted household record. Another computer is a **member**: it keeps a usable local copy, including changes made while away. When both can reach each other, a member **pulls** accepted changes from main and **pushes** its own changes as one change request. Main shows that request on **Review**, with a before/after view and **Accept / Reject** for each row. Nothing from a push changes main's live records until a person accepts it. A member only receives accepted changes on its next pull. Main must be running and sharing switched on to exchange changes. The member can still work offline.

The mode badge (0082) links to Settings → Sync and says **On this computer only** until setup is complete. While paired it says **Syncing with Sam's desktop · last pulled 20/11/26 7:40 pm** (time and date in the household's format). Offline it says **Sync paused · changes saved here**. If there are incoming requests on main: **Syncing · 3 changes to review**. The page must show both **last successful pull** and **changes waiting to push**; “last synced” alone could imply an unreviewed push was accepted. Printed sheets should state the copy's accepted-main revision and print time, so an offline member does not mistake an old sheet for current information.

This is opt-in. Pair one member at a time from main's Settings → Sync using a short-lived, single-use invitation and a separate **household member key**. A helper key (0066) must never work for sync. A member gets the full copy of parts switched on, subject to the fixed field policy below. The main screen names what will copy, including medical safety details. Member access is to a copy, not a live browser session. The member has a named device entry on main with **Turn off this member**. Revocation stops future pull/push, but cannot erase what the member already received.

### What travels

Decision 0089 requires a per-column **travels to members** classification in the exchange schema. The shipped `sensitive` flag controls Show and printing; it alone cannot decide travel. In v1, `people.important_info.detail` travels when `kind` is allergy, condition, medication, care_need or dietary. These are medical safety details: members keep the Show protection and may print them on the emergency sheet. `kind=access` never travels. `kind=other` needs a product classification before it can travel; default to local. `home_layout` access_details on homes, rooms, storage and spots, and `vehicles.registration`, never travel. The item 69 proposal for a household **Private details On** grant is withdrawn. A newly added private column defaults to local until reviewed and classified. Record text, names, links, status, notifications and summaries must not duplicate a local-only value.

A local-only value stays on the computer where it was typed, whether main or member. On a member looking at a value held by main, show **Kept on main** in its field, with no Show button. For a value typed on this member and absent from main, main shows **Kept on Sam's laptop** without a value; if even the existence or device label would reveal a secret, show only **Kept on another computer**. The field's transfer status must never be mistaken for an empty value, and syncing must not erase either local copy. If `kind` changes to or from `access`, strip the detail from outgoing operations according to the new classification and require a local edit to replace an old remotely copied value; neither direction silently clears it. Stage 1 must decide this transition and its rollback before exchange ships. Backups and ordinary exports remain local data operations; their privacy and encryption rules are separate from sync.

## Reach main privately

The private-network layer is pluggable: Tailscale and self-run WireGuard are the initial adapters; a third can be added without changing record IDs, member keys, Review requests or the exchange format. An adapter supplies a selected private address, peer reachability and network-change events. Dashboard owns pairing, app authentication, TLS identity, authorization and sync cursors. Main binds the sync listener only to the selected private-network address, **never `0.0.0.0` or a public router address**, and only while **Allow sync** is on. Switching adapters or addresses closes the listener, requires the member to verify main's pinned identity at the new endpoint, and resumes from its cursor without treating the network switch as a data merge. Local screens and the helper API stay on loopback. Tunnel loss, sleep, app close, revoked membership and a restore pause close the listener; after restart sharing remains off until the household deliberately switches it on again. A home server is a later milestone.

Use HTTPS even inside the private network, with main's certificate/public-key fingerprint compared and pinned during pairing. A member refuses a different certificate on every later connection; show **This may be a different computer. Sync stopped. Compare its identity on main before pairing again.** A short invitation code alone does not authenticate main. Conversely main challenges a member to prove possession of its member key before sending records. Use the principle of 0086: a fresh nonce, a proof tied to the intended main identity and the same checked connection for the authenticated request. Use distinct domain strings and separate key stores from `/api/v1/hello`; never reuse the helper fingerprint or grant. Normal TLS client verification, key rotation and replay resistance need a reviewed protocol, not copied formulas from 0086. No key in URL, log, QR content shown to bystanders, exported file or backup. Each device gets its own key; revoking one must not affect another.

Do not tell a household to forward a router port or use a public tunnel. That would make the sync door reachable by uninvited internet clients and expose a larger, newer attack surface. Private-network membership is an additional gate, not a substitute for Dashboard's member authentication, exact Host checks, rate limits, bounded request bodies, replay protection and per-module authorization. Main's Settings/Restore/Export/Helpers pages remain local-only. An independent security review is required before shipping.

## The record and exchange model

Each installation has a random **device ID** and each household a random **household ID**. Each module row, including stock batches, movements and linked rows, gains a stable random **global ID** in addition to its current local integer ID. Foreign keys in an exchange refer to global IDs. Main maps them to local IDs only inside a checked transaction; a missing target remains a Review problem. IDs are never derived from a person's name, a timestamp or the local row number.

Every accepted edit writes an immutable sync change beside `core__audit` **in the same transaction**: household/device IDs, device sequence, operation ID, table and global row ID, module/schema version, base main revision, observed row version, changed fields (or tombstone), actor and time. Audit remains the local human history; its local `record_id` and entry ID are not a portable sync protocol. Main assigns a monotonic **main revision** after each accepted change. The member keeps a cursor for the last fully verified pull and a durable outbox of local operations. A retry sends the same operation IDs. Main stores their decisions so retries cannot stage or apply twice. Wall clocks are for display only; do not order conflicting edits by whose computer clock is later. A row version is an opaque main revision plus the member's base, with explicit conflict detection; hybrid clocks add complexity without removing the need for human Review.

**First pull:** main sends a consistent, versioned snapshot of the parts switched on, links and tombstones plus a cursor, filtered by the field policy above. Before applying it, the member makes a checked local backup (0079). Download into a bounded temporary file, verify identity, manifest, digest, schema, links and completeness, then apply atomically. If interrupted, leave the old copy in use and retry. **Later pulls:** request changes after the saved cursor, in bounded ordered pages; save the new cursor only with the applied records. A cursor from a different household, an older restore epoch or a pruned log requires a new checked snapshot, not a guessed continuation. Local-only fields are represented by a protocol marker with no value, hash, length or search token; a missing value must never mean clear it. Apply the same filter to push, pull, Review staging, conflicts, logs, bundle files and error responses. Do not put a local-only value into the portable change log at all.

**Push:** the member sends its durable filtered outbox since the last acknowledgement, with the base main revision for each changed row. Main authenticates the device, checks membership/schema/links and stages one named change request on Review. Staging is not acceptance. It returns a durable request ID and per-row status; network retry with the same operation IDs returns that same request. Local-only fields are deliberately withheld with a visible local status; a whole row must not be silently dropped because a module is off or a version differs. After the person decides every row, main records the decisions and accepted changes atomically in its own log; a member sees accepted/rejected/rework states on its next pull. A rejected local edit remains visible in the member's “Needs your attention” until the person chooses **Keep only on this computer** or edits and resends it.

## Review and conflict rules

The request header says **Changes from Sam's laptop · 4 rows · sent 19/11/26 8:10 pm. Nothing has been added here yet.** Each row shows **Main now**, **Sam's change**, the member's **Based on** value and a plain reason if it cannot be accepted. Buttons: **Accept this change**, **Reject this change**; disabled **Accept** explains what must be fixed. A batch-wide Accept is allowed only after every row passes validation against the current main state, in one transaction. Review rechecks under the write lock at decision time, as in 0088. Only a person at main can decide. The member cannot approve its own request or send a helper suggestion through this door. Review must escape and label member text as untrusted, as for helper proposals (0074).

| Incoming situation | Decision on main |
|---|---|
| Different fields of one row changed since the member's base | Show both; accept only the member's changed fields after validating the combined row. Never replace the whole row with the stale member copy. |
| Same field changed on both copies | Show both values side by side; person chooses main's value or member's. No silent last-writer rule. |
| Two independent Stock in/out movements | Keep both distinct global movement IDs; apply each exactly once through Stock's normal movement logic. Never copy cached item/batch totals. Reject or pause a movement that would make a batch negative or break another invariant. |
| Member stocktake count | Send the counted amount, batch global ID, observed amount and base version, not a precomputed delta. At Review, compare with main's current batch and list intervening movements. If different, require a fresh human decision about the count; only then compute a correction under one write lock (0070). |
| Delete against a newer edit, or edit against a delete | Show the tombstone and changed fields. Person may keep deleted or retain/edit the record, with links revalidated. Never resurrect it by ordinary pull. |
| Module absent, off or older on either copy | Hold the affected row as **Waiting for compatible module** with no apply and no name/private-value disclosure outside authorized views. Unaffected modules may continue only if no cross-module dependency is broken. |
| Restore on main | Pause sync and advance a household **sync epoch** after a confirmed restore or Undo. No old member cursor or queued push is replayed automatically; compare and re-pair/rebase it explicitly. |

Tombstones stay until all paired devices acknowledge them or are explicitly retired; pruning a log is safe only after a checked snapshot/cursor rule accounts for long-offline members. Module migrations need a versioned exchange schema and upgrade path for old queued operations, not merely a new SQLite schema. Preserve unrecognized incoming bytes in a bounded, access-controlled staging store for diagnosis; never inject them into a disabled module or print them on a sheet.

## Offline file bundles

**Export sync bundle** on a member writes the same versioned operations and base cursors to a file; **Import sync bundle** on main stages the same Review request. Main can export accepted changes for a member's next pull. File exchange does not bypass idempotency, schema checks or Review. Encrypt and authenticate each bundle with a **separate pairing secret**, a modern AEAD format, random nonce, household/device IDs and sequence in associated data; reject tampering, wrong household, old epochs and reused operation IDs. Python's standard library does not supply an appropriate AEAD primitive, so dependency and key recovery need a separate decision. Never copy an open SQLite database or put a raw member key in a bundle. Lost USB sticks can expose ciphertext and metadata (size/time); a stolen laptop can expose its local database unless device storage is encrypted.

## Moving main and turning sync off

Moving main to a home server is a **handover**, not a member taking the old main's name. Main pauses pushes, makes a verified backup and a handover package of accepted snapshot, log/cursors, pairing roster and a **new server identity**. The new server checks and imports it while offline, then each member compares/pins the new identity in person. Old main revokes its listener and signs a one-time handover marker; simultaneous old/new mains must be refused. A portable headless build needs a supervised process, private-network binding and a way to administer backup/restore locally; this is a separate product and security milestone.

**Pause sync** stops the listener and exchange; records and pending requests remain. **Turn off this member** revokes that device's key and blocks all future exchange. **Stop syncing this household** keeps the local accepted copy and offers a checked backup; it does not remotely erase other copies. These actions must say that records already copied to another computer remain there. On a lost laptop, revoke its key from main and rotate the pairing/bundle secret, then assess whether disk encryption protected its saved copy. A mistaken member edit stays pending until Review; an accepted mistake uses the existing correction/Undo rules, with a new accepted change sent to members rather than rewinding history.
