# From the Mac preview to a proper release

Batch 24 item 128. Planned **27 November 2026**. This is a release plan, not a claim that a signed Mac app exists. The current Apple silicon `.app` is an **unsigned preview** built and smoke-tested in CI; nobody has recorded a clean, downloaded, real-Mac household test. Intel, Developer ID signing, notarisation and automatic updates are not shipped.

## What the household would see

1. Download one clearly named Mac release for their processor, or a universal build only after both processors have been tested. The download page says the minimum macOS version, release number, checksum and whether this is a tested release. The normal release opens without instructions to bypass Mac security warnings.
2. Move **Dashboard Plus.app** to Applications and open it. A Dock icon and small **Dashboard Plus** menu offer **Open dashboard**, **Backup status** and **Save and exit**. The main work remains in the browser. Quit waits for the server to stop and the safe-close backup result; it never closes just the browser tab and leaves the program running invisibly. If startup fails, an alert points to a local, privacy-safe report and the help page.
3. Records remain in this Mac account's `~/Library/Application Support/Dashboard Plus/`, separate from the replaceable app. The current second backup remains in `~/.local/share/dashboard-plus/backups/` until Lane A explicitly migrates it. Both are on the same Mac by default; a household also needs a checked copy on another device or drive for computer loss.
4. An update says what will change, asks the person to **Save and exit**, verifies a Dashboard backup, installs a complete signed app, then reopens the same records. It warns before a data migration and offers the supported way back. Replacing the app must not delete Application Support or claim that an older binary can open a newer database. First release may use a verified **manual update**; an automatic updater follows its own trust and recovery checks.

The present preview has no Dock icon or menu because its `LSUIElement` flag hides them; its launcher exits after starting a background server. A proper Dock/quit flow therefore needs a persistent Mac app process or another reviewed lifetime design. Merely changing the flag would not give a reliable menu or stop action.

## Build order for Lane A

| Step | What to build | Decision gate |
|---|---|---|
| 1. Finish the preview test | Download the exact CI zip on a real Apple silicon Mac, quarantine and all; install, open, save and exit, reopen, replace with a newer preview, restore a made-up backup, and check the data and second backup paths. | User 1 or another Mac tester supplies macOS version and observed screen words, without household records or personal paths. A CI launch from its build folder is not this test. |
| 2. Choose processor support | Keep a named Apple silicon release and make an Intel build if real Intel support is wanted. A universal build comes only if every bundled executable and library has both slices and both are tested. | Publish supported macOS versions and processors; never silently rely on Rosetta. |
| 3. Make a trustworthy download | On a controlled Mac runner, sign the app and every nested executable with Developer ID, hardened runtime and secure timestamp; verify the final signature. Submit the finished distribution artifact to Apple's notarisation service, staple where supported, and test a fresh download with Gatekeeper on. | Failed signing, notarisation, stapling or clean-Mac launch blocks release. Never ask a household to turn off Gatekeeper for a release. Notarisation is not App Store review. |
| 4. Give it a visible lifetime | Give the running app a Dock icon and menu, one server per data folder, browser reopen, reliable Save and exit and a clear failure report. Keep the local listener on loopback unless a separately reviewed sync release deliberately enables a private interface. | Test quitting from menu and page, closing only the browser, slow start, crash and two attempted launches. No hidden second process or lost backup. |
| 5. Release with manual updates | Publish signed versioned downloads, checksums, release notes and a tested replace-the-app path. The app checks data version before opening and makes a verified backup before migration. | Practice a failed install and a failed migration, then restore the prior data from the checked backup. Do not promise a binary-only rollback of migrated data. |
| 6. Decide on automatic updates | Later, choose a signed update mechanism and document how it authenticates a release, downloads it, verifies hash/signature/notarisation, stops the app, replaces the whole bundle and reports failure. | A downgrade, broken network, altered download and interrupted install leave the old app and records usable. Adding an updater dependency needs a separate decision under `AGENTS.md`. |

Signing does not encrypt the household database. The program still runs on this Mac; an online helper the household connects can receive only its permitted information, and later computer sharing remains a separate consent-based feature. A signed Mac release should state the actual sharing status at its release date.

## Account, money and release responsibility

For a direct download outside the Mac App Store, User 1 needs access to an **Apple Developer Program** team that can issue a Developer ID Application certificate and submit for notarisation. Apple's listed membership is **US$99 per year** (checked 27 November 2026; local currency and tax at checkout can differ). Enrollment and identity verification come before certificates. Lane A can prepare the build and a test artifact without a certificate, then ask User 1 to enrol or grant a controlled team role for signing. Do not put a certificate, private key, Apple login, notary credential or household data in the repository or a PR. A release owner should approve the final artifact and the words on the download page. An App Store release would add sandboxing and App Review work and may change the data path; it is not part of this first direct-download path.

Costs beyond membership are Mac CI or build time, an Intel test Mac if Intel is supported, real-device testing, signing secret maintenance, release hosting, support for updates, and accessibility review. The design should not buy a new updater or packaging dependency until the manual path and failure recovery are proven.

## Backups and Time Machine

Dashboard already makes checked SQLite backups inside Application Support and a second local copy under `~/.local/share/dashboard-plus/backups/`. **Time Machine can back up user files**, but an untested copy of a live SQLite database is not proof of a usable Dashboard restore. Keep Dashboard's checked-backup flow, verify a backup before an update, and practise restoring it on a clean Mac account. Test Time Machine restoration of a safely closed Dashboard backup as an extra recovery route. Say when the last checked backup was made, where the second copy lives, and whether an external or off-Mac copy exists. Removing the `.app` leaves records and backups; erasing them is a separate deliberate household action.

## Acceptance checks before calling it a release

1. The final downloaded artifact installs and opens on clean supported Apple silicon and, if offered, Intel Macs with Gatekeeper active. `codesign`, `spctl` and notarisation-ticket checks agree with the published version; no **Open Anyway** step is required.
2. The Mac without developer Python opens the browser, loads every switched-on module and helper address file, and refuses a forged browser launch token. Only the expected local listener exists. Quit from page and Dock menu both stop it and show a successful or failed backup accurately.
3. Open, close the browser tab, reopen from Dock, start twice, slow the startup and crash the server. Every state has an understandable recovery action; no unseen process keeps using the data folder.
4. Save records, update the app, and restore an invented Windows backup into a separate Mac account. Record IDs, dates, sharing choices, retired sensitive fields and backups stay correct. Test interrupted download, wrong processor, bad signature, full disk, migration failure and too-new data without damaging the original copy.
5. Check owner-only data permissions, symlink and removable-folder refusal, different Mac accounts, backup locations and Time Machine restore. The two local backup folders on one disk are not described as a computer-loss backup.
6. Test VoiceOver, keyboard and large text on the browser and the small Mac menu; check Dock name, app icon and failure alert. The downloaded read-me must match the shipped build and its real privacy/sharing behavior.
