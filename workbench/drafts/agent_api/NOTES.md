# Agent API draft notes

Updated **19 November 2026** after the API merged (decisions 0066–0069, 0074, 0084–0086). [ABUSE_CASES.md](ABUSE_CASES.md) remains the original design and test catalogue; the [dated live recheck](../../reports/2026-11-19-agent-api-abuse-recheck.md) says which of its 22 cases hold on current `main`. The shipped OpenAPI description at `src/dashboard/web/openapi-v1.json`, served by `GET /api/v1/openapi.json`, supersedes this draft folder's `openapi-v1.json` and `OPENAPI_NOTES.md` for client generation.

The plan already covers bearer-only auth, local Host and Origin checks, module grants, private-field exclusion, staged suggestions, idempotency, bounded bodies and a daily proposal cap. The highest-priority behavior to verify in the build is **no live side effect before a person accepts** and **no hidden module name, ID or private value in any response or proposal validation**. A local program that has a key is authorized within its grant; Origin checks cannot stop local malware or a key willingly given to an online service.

**Current core gap:** request throttling, a 200/day cap, a 500-waiting cap, hidden-link protection, helper-text screening and one 404 for unknown or ungranted tables have shipped. The two suggestion caps can still be exceeded by simultaneous requests because their counts are read before the insertion transaction. Move their final checks inside the write transaction and add concurrent tests; see the dated recheck for the exact temporary-household reproduction. An unsupported `/api/v2/` request also redirects to the page start instead of returning a JSON 404. A future MCP connector still needs an untrusted-record-text test before it can ship.

Item 51 adds [later change-suggestion screens](CHANGE_SUGGESTIONS.md) and [acceptance checks](CHANGE_ACCEPTANCE.md). V1 is still add-only; these need monotonic revisions and person-only conflict/undo services before any endpoint is exposed.

Item 52 adds a [local stdio MCP design](MCP_CONNECTOR.md), [eight-tool manifest](mcp-tools.json) and [acceptance checks](MCP_ACCEPTANCE.md). The connector has now shipped (decision 0083), including an identity check before it sends a key (0086). Its acceptance run remains item 63; the original draft and manifest are design history.

Item 60 adds the [household quick-start](HOUSEHOLD_QUICK_START.md), checked 19 November 2026 against `src/dashboard/web/templates/helpers.html`, `helper_key.html`, `helper_connect.html`, `src/dashboard/web/helper_settings.py` and decisions 0066–0068, 0074, 0083, 0086–0087. It uses the settings block generated by the running app, so no personal paths or live keys are in the draft. **Core gap:** the Dashboard address changes every launch, so the person must replace the assistant app's MCP settings after reopening. Item 65 below designs a steady locator but it is not shipped. There is no tested setup path for a named assistant desktop app or a way to know where that app saves its key; before publishing app-specific instructions, core/product needs a supported-client test and a storage warning for that client. Browser-only assistants that cannot launch a local MCP server cannot use this connector.

Item 65 adds [steady address discovery](STEADY_ADDRESS.md), checked 20 November 2026. It recommends a separate, secret-free `data/run/helper-address.json` updated on each start and read on every connector call, with decision 0086's identity proof still required. The current `data/run/dashboard.json` also contains a launch session and shutdown token and must not become the connector's file. The preferred Settings block, file lifecycle, per-call resolution, limits and ten checks need core work. Existing manual copied-URL setup remains the compatibility path; until a change ships, the quick-start's restart instruction is accurate.

Item 66 adds [one-step key rotation](ROTATE_KEY.md), checked 20 November 2026 against the shipped helper row, secrets file and Review linkage. The stable helper `id`, `key_id`, slug and grants preserve its history; one atomic secrets-file replacement removes the old fingerprint and adds the new. Core still needs a helper-bound one-use form token, fail-closed pending state and recovery across database/file writes, an in-flight proposal recheck, a value-free audit event and one-time response. A turned-off helper must not be re-enabled by a stale rotation form. The present Turn off + Add helper path creates a separate history and is not called rotation.

Item 53 adds a [future one-field private grant](PRIVATE_GRANT.md) and [acceptance checks](PRIVATE_GRANT_ACCEPTANCE.md). V1 continues to share no sensitive fields; a grant needs a dedicated API route, durable revision, one-read consumption and restore-safe revocation before it can ship.
