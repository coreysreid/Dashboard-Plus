# Recognising a receipt sent twice

Design only, checked **21 November 2026** against shipped helper request idempotency, decision 0097's source lines and grouped Review, and decision 0094's spreadsheet import warning. All records below are invented. The current `request_key` protects **one helper's exact retry**; a new key, a second helper, or a spreadsheet import can still stage the same purchase again. Generic CSV import warns about a Stock item name already present, but does not know whether a group of Stock in rows is a repeated receipt. This design adds a **possible-duplicate warning**, not an automatic refusal of a legitimate second shop.

## Which work is one receipt

A helper that read one receipt sends its clear proposals (and any unmatched line form from [UNMATCHED_LINES.md](UNMATCHED_LINES.md), once built) in one group with an optional, closed `receipt_context` on the request: `{ "purchase_date": "2026-11-20", "shop_label": "Example Market" }`. The date must be a real ISO date and is a *receipt claim*, checked by the person; the shop label is optional visible text of at most 80 characters, never a payment or loyalty reference. Screen and validate it like other helper text. The helper does not attach a full image, card digits or customer ID. For an older helper that sends only per-entry `source` lines, Review may offer **“These look like one receipt. Check for a repeat”** but must not silently declare an exact receipt group from its `why` prose. The connector's current request remains valid without the new context.

On **Import from a spreadsheet** for `stock__movements`, offer an unticked **“These rows are from one receipt”** checkbox after mapping and dry run. If chosen, ask for the purchase date and use only the rows sent from this file as one receipt group. One file with several receipts needs separate imports or an explicit grouping column in a later design; never treat its file name as proof of one purchase. Ordinary Stock item/Place imports are not receipt groups. The uploaded file stays in the current memory-only import flow; no raw CSV or photo is kept as a duplicate-detection key. If a source line is available in a future receipt-specific CSV, keep it under decision 0097's Review-only source rule, not in Stock.

A receipt group records its **origin** (`helper` or `import`), the optional date/shop label, its Review batch ID and each accepted movement's permanent record ID. This local Review metadata stays in the household backup, but not in Stock fields, the general spreadsheet export or stage 1's portable change log. Stage 2 must separately decide whether receipt-origin metadata travels; the Stock movements themselves follow the ordinary travel rule. A skipped/rejected line has no movement ID.

## When Review warns

Before any Accept on a receipt group, build a candidate basket from its ready bought movements: a **multiset** of `(purchase date, item identity, amount in the item's saved unit)`. Keep repeated identical lines twice; do not sum or collapse them. An existing item uses its permanent ID. A proposed new item uses normalized name **and unit** as a provisional comparison only; it cannot be treated as the same permanent record until a person chooses it. Ignore row order, case and extra spaces, but do **not** ignore quantities, units, dates or repeated lines. Do not use price as proof: the same goods can have different discounts and a line's price is helper-supplied checking text. Do not fingerprint raw receipt text, payment fields or a whole CSV file. Compute comparison from the accepted movement facts and local Review group records; index by date and group ID if needed, rather than storing a low-entropy plain hash of a basket.

Compare with earlier receipt groups, including ones **still waiting or partly accepted**. If all confident existing-item rows match the same dated basket in an earlier group, show a high-priority **possible repeat** warning. An import group and helper group can match this way; route and filename do not matter. If new-item identity is provisional, dates are missing/ambiguous, only a subset matches, or one group has unmatched lines, say **“Some lines look like an earlier receipt”** with the differences and ask the person to review; never call it the same receipt. A different place or use-by lot can still be the same purchase, so those are shown as differences but not part of the basket key. A receipt that was fully undone is shown as **“Earlier receipt was undone”**, not as an active duplicate; a partly undone receipt shows which movements remain.

The guard is recomputed inside the same write transaction as Accept, under the ordinary write lock, so two tabs cannot both accept the same basket after each saw an old Review page. A direct POST and **Accept all** use the same guard. If the warning first appears at save time, refuse that save with no partial Stock writes and return to Review. A household may deliberately keep a true second purchase: one explicit **“Keep this as another purchase”** decision applies to this group only, is recorded with the earlier group ID and current group revision, and is rechecked at the next Accept. It does not authorize later lookalike groups.

## Exact screen words

For an exact basket match with an earlier accepted or waiting group:

> **This may be the same receipt again. Nothing from this copy has been added.**  
> These 3 goods, amounts and purchase date match a receipt put on Review on 20/11/26 by Example receipt helper. It may still be waiting, or may already be in your Stock. Check the earlier group before accepting this one.  
> **Open earlier receipt** · **Reject this copy** · **Keep this as another purchase**

Show the earlier group's actual state directly under that text: **“Already added: 2 Stock in rows; 1 new item and its Stock in”**, **“Still waiting: 3 rows”**, or **“Partly added: 1 of 3 rows.”** Never say “already added” for waiting rows. If the earlier group came from a spreadsheet, say **“from your spreadsheet import”** and its safe file label instead of a helper name. If the current group has unresolved lines, change the first sentence to **“Some lines look like an earlier receipt”**, list the matched count and missing/changed lines, and withhold the **Keep this as another purchase** shortcut until the household has chosen or skipped those lines.

**Reject this copy** rejects only the current waiting group (including dependent new-item rows) and says **“Rejected this copy. No Stock amount changed from it.”** It never deletes the earlier group or its Stock movements. **Keep this as another purchase** says **“Treat this as a separate purchase. Check each row before accepting.”** Then the normal Accept and Reject buttons become available; it does **not** add anything. If another group changes in the meantime, the decision expires and the warning is recalculated. A reviewed duplicate does not bypass normal Stock validation, stale count checks or use-by/place choices.

On import dry run, before Send to Review, show a lighter early warning when the mapped rows already match: **“These receipt rows look like one you added on 20/11/26. You can still send them to Review, where you must choose whether this is another purchase.”** Date ambiguity (decision 0094) must be resolved first. Import never auto-skips a row or silently drops a repeat; Review is the final decision point. On exact `request_key` retry, return the original batch and do not create a second Review group or a new warning.

## What core needs

The current `core__helper_batches` knows helper/import origin and request key, but not a confirmed receipt group, cross-route basket or which accepted movements belong to that receipt after later Undo. Add local receipt-group metadata and a checked lookup over accepted/partly accepted movements. Keep it out of Stock notes, receipts' raw images, general export and stage 1 portable logs; a checked backup retains it so a restore can still recognise its own history. A restore/Undo changes epoch and requires the candidate lookup to use **current active movements**, not a stale cache. If the record source is too old or missing, label evidence as incomplete instead of claiming a match.

The helper API and connector need one optional `receipt_context` object. CSV import needs the explicit one-receipt choice and date, staged as the same group kind. Review needs prior-group links, state-aware wording, the one-group override decision, and a transaction-time guard shared by row Accept and Accept all. A receipt-wide Undo is still a separate operation; this design only notices possible repeats. A fingerprint alone cannot settle whether two equal baskets on one day are distinct purchases, so household confirmation remains required.

## Acceptance checks

1. Retry one helper request with the same `request_key` and same body. The API returns the same batch ID; Review has one group and no extra Stock movement. Reuse that key with a changed body: 409 refusal and no second group (existing behavior).
2. Submit the same three invented bought rows with a **new** request key and matching receipt context. The new group stays waiting under the possible-repeat warning. No Stock count changes from it until the person decides.
3. Submit those rows through receipt-mode `stock__movements` CSV import with the same date and mapped item IDs. Review warns and links the helper group even though the route and filename differ. An ordinary Stock-items CSV does not claim to be a receipt.
4. Change order, case and spacing of the helper's source lines, or change prices only. The same basket still warns; price text is not a Stock value. Two identical product lines stay two multiset entries, not one summed row.
5. Change one amount or unit, leave one date ambiguous, add an unmatched product line, or propose a not-yet-created item with a similar name. Review says **“Some lines look like an earlier receipt”** and names the difference, never an exact duplicate. No inferred item ID or date is saved.
6. Stage two identical groups in two browser tabs and try Accept on each concurrently. Under one write lock, the first may save; the second sees the updated earlier state and stops before any of its movements are added. A direct POST cannot bypass the warning or the one-group override.
7. In a true second same-day shop, choose **Keep this as another purchase**, review each row and Accept. Both purchases remain distinct with separate movement IDs and a recorded decision; a third identical group warns again. The override expires if the earlier group changes before save.
8. Choose **Reject this copy**. Only this group's waiting rows become rejected, including a dependent new item/Stock in pair; the first group's Stock, Review history and amounts remain unchanged.
9. Accept only one row of the first group, then stage the second. The warning says **“Partly added: 1 of 3 rows”**, never “already added.” Finish or reject the remaining rows and verify the state updates.
10. Undo all movements from the first receipt through ordinary Stock actions. A later matching group says the earlier receipt was undone and asks for review without claiming active duplicate Stock. If one movement remains, list it as partly undone.
11. Import the same CSV twice with the checkbox selected. The second import warns on dry run and Review even with a different file name. An unclear date must first pass decision 0094's date confirmation; no suggested match silently settles the date.
12. Put a key-shaped string or hidden direction mark in helper context or source: the API refuses the request before staging. Put a 16-digit payment-shaped number in a receipt line: the new receipt validator refuses it or requires the helper to crop it before sending. A raw photo, payment line and plain low-entropy basket hash never enter the duplicate ledger. A general export and stage 1 portable snapshot contain Stock records but no local receipt-group metadata.
13. Restore a checked backup and Undo restore. The guard recomputes from the current active groups and movements; no stale pre-restore accept decision or cached match can authorize a new duplicate. Backup contents retain only the allowed local metadata.
14. Test 201 prior receipt groups and a long 50-line candidate. Matching remains bounded and preserves all line occurrences; a too-large helper batch is refused by the existing 50-entry limit with no partial group.
