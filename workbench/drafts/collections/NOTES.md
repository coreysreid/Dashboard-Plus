# Collections: promotion check

Rechecked **19 November 2026** against shipped Stock Places, helper/API and export privacy, `docs/DESIGN.md` §§5.5 and 5.8, and decisions 0072/0075/0078. Examples and values are invented. This is batch 14 item 58; no market prices or appraisals are supplied.

**Not ready for the full household promise yet.** The draft can record collections and items today, and `items.place` already links shared `stock.places` with a full path. Its owned-item place question uses the now-supported `where` filter. Neither linked sheet phones nor a one-step action is required. A sale needs a person to enter a date and optional amount, so the current fixed-value one-step button is not the right tool; use the edit form.

**Total value needs a core aggregate card.** On a collection page, add `value_now` only for current, nondeleted items with `status = owned`; count how many owned items have no estimate. Say **“Your estimated value now: $95 across 2 of 2 owned items”** or **“$60 across 1 of 2 owned items; one has no estimate.”** Recompute after edits, sales, deletions and restores. A blank is unknown, not zero, and `sold_for` never enters this total. Show the household currency and never call this an appraisal, sale price or insurance replacement value. The current declarative core has no such aggregate-card contract. Lane A could promote a smaller list-only version only after explicitly removing the total-value promise.

**Sale form is partly supported already.** The old note that the core cannot conditionally show fields is stale: `labels.toml` can use `show_when = { status = "sold" }` on Sold for/Sold on, and `tables.toml` can use `required_when = { status = "sold" }` for Sold on. Add those declarations and regenerate the unreleased migration before promotion. The draft still needs a rule or a stated smaller scope for an owned item carrying a sale amount/date after a status edit. Keep the sold record and its last estimate for history, but exclude it from the current total.

**Value privacy needs a choice.** `bought_for`, `value_now` and `sold_for` are ordinary money fields; `value_now` is on the list and all three can reach a granted helper and the general spreadsheet export. The sheet omits values and notes but prints full place paths. If the household wants values hidden by default, mark the fields sensitive and decide how a collection total may be revealed without leaking private amounts in list HTML, helper responses or export. The existing core supports private field reveal and private-sheet choice, but no aggregate-card privacy rule. The collection's ordinary name and place remain visible. A field-privacy choice is needed before promotion, not a promise that the current draft is already private.

**Order:** Wine is first; Utilities is closer once its current links and sheet are revised. Collections follows after its total/sale scope and privacy choice. No cross-module place migration is needed: Home layout uses `stock.places` (decision 0054).
