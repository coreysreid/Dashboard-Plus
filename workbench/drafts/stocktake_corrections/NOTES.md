# Stocktake correction contract and core needs

Design checked **18 November 2026** against shipped `modules/stock/tables.toml`, `tests/test_stock_batches.py`, decisions [0043](../../../docs/decisions/0043-records-that-change-a-count.md) and [0053](../../../docs/decisions/0053-batches-for-layered-use-by-dates.md), and the later stocktake screen fix in #96. This is a **draft**, with no shipped-code changes. Current behavior lets a person edit a batch amount; the item total follows and record history keeps the edit, but Stock in and out has no separate correction entry. The item amount is derived and cannot be typed over.

## Proposed record

One confirmed count difference creates one `stock.movements` row linked to the exact item and batch. Add stable reasons `counted_more` and `counted_less`, both displayed as **Stocktake correction** with a signed amount. Store the positive absolute `amount`, the count date, chosen batch ID, and a snapshot of **recorded before** and **counted after** for an intelligible audit. `counted_more` is an add in `adjusts`; `counted_less` removes. The item total follows the batch `total` rule. Keep those reasons separate from Bought or added, Used, Expired, Thrown away and Given away, so later shopping and waste views do not misclassify a discrepancy. This is a delta movement, **not** a “set to 5” movement; later stock in/out remains independently reversible.

The review action compares the batch's current amount and revision with what was shown. Within one database transaction it validates the expected revision, writes the movement and updates the batch/item totals exactly once, and records before/after audit. A retry or double click uses an idempotency key. The current `updated_at` timestamp has only second precision, so it cannot by itself be this revision; core needs a monotonic batch version or an equivalent durable compare-and-swap value. If the current count or revision differs, stop and review again. Reject negative or unsupported precision, a batch from another item, a deleted batch, and an increase on a batch that should instead be a new date/place. The person may still choose to count an undated batch; no date is invented. A correction is counted on the day of the count, with that day's local display format; a historical backdated count would need a separate as-of balance design.

**Undo and edits:** Show a correction as its own Stock in and out row with the signed difference and the source count. Undoing or editing it must apply only its delta and preserve an audit trail. If removing a `counted_more` row would put a later batch balance below zero, refuse with the current amount and ask the person to reconcile later movements first. A `counted_less` undo adds the same amount back. Never replay a restored movement twice. The existing direct batch quantity edit should not silently create another correction; after a batch is created, its count edit should enter this flow or be explicitly named as an administrative change with separate history.

## What the core and screens need

The shipped `adjusts` rule has add/remove reasons and batch ownership, but no dedicated count-review form, compare-and-save revision check, idempotent confirmation token, before/after count fields, or reason labels for the two correction directions. It also does not record a direct batch edit as a movement. Lane A needs those pieces to make [SCREENS.md](SCREENS.md) truthful. This design does not work around them with a fake Bought or added/Thrown away entry. A later cross-batch stocktake should ask for each batch separately or present an explicit reviewed split; it must never guess which use-by date lost tins.

These quantities and dates are invented test data, not shelf-life or shopping advice. No external preparedness claim is made.
