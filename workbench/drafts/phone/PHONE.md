# Android and iOS as household sync members

Designed **20 November 2026** for batch 17 item 73. Decision 0089 makes each phone a **member** of the same household sync: it pulls main's accepted records, works offline and pushes changes to main's Review. Main still decides every incoming row. This is a design, not a shipped app. Two computers come first; phone work begins after the shared protocol and stage 0 review are stable.

## Options and recommendation

| Option | Offline records and workflow | Private-network and key work | Delivery cost and constraint |
|---|---|---|---|
| Installable web app (PWA) | Service worker caches the shell; IndexedDB or OPFS would need a durable, versioned local record store and explicit offline outbox. Background transfer and storage retention need phone-by-phone tests. | A separate Tailscale/WireGuard phone VPN might let the web app reach main, but browser origin, HTTPS, pinning, key storage and background behavior need proof. An ordinary web page cannot take over an OS VPN. | One web UI can reach both platforms without store accounts, but building a safe offline sync client in browser storage and the platform-specific limitations are substantial. A browser-accessible member secret is a security concern. |
| Cross-platform packaged app (recommended first phone build) | One shared client implementation with platform adapters, a durable local database, foreground sync, and explicit retry/outbox state. Test offline writes and crash recovery on both systems. | Use OS key protection for the member secret, app-owned main identity pinning, and the user's separately installed private-network client at first. Native bridge may be needed for network state and secure storage. | One UI/codebase lowers duplicate screen work, but needs iOS and Android build, signing, store compliance, native dependencies, two device test matrices and ongoing OS updates. A framework such as Flutter is a candidate, not an approved dependency. |
| Separate native apps | Platform SQLite, Keychain/Keystore and network APIs fit naturally; full control over accessibility and background rules. | Two pairing and network implementations must remain protocol-identical. | Highest engineering and review cost, but best route if a shared framework cannot meet security, offline or accessibility checks. |

**Recommendation:** a cross-platform packaged member app, with foreground sync as the first supported behavior and an external private-network app configured by the household. Evaluate the framework after the stage 0 security review and a small two-phone prototype. Keep the wire protocol, field filter, revision/cursor rules and Review statuses platform-neutral; do not embed Windows paths, desktop browser tokens or provider-specific peer addresses. Do not promise automatic background sync until both OSes prove it reliable. A PWA is useful for screen exploration, but its secret storage, long-offline data and private-network path need too much unproven behavior for the first trusted member.

## Pairing, data and network

1. Main's Settings → Sync shows a short-lived, one-use invitation and main's identity fingerprint. On the phone, **Add this household** scans or types the invitation, then displays main identity for comparison with main's screen. Do not put a long-lived member secret in the QR. The app generates or receives a device-specific member credential according to the reviewed protocol, keeps it in iOS Keychain or Android Keystore-backed storage, and shows only a device name on main. A helper key cannot pair a phone.
2. The household installs and joins Tailscale or a self-run WireGuard phone client separately. The phone app checks that the chosen main endpoint is on that private network and that its app-level pinned identity matches. The VPN alone never grants Dashboard access. If iOS/Android VPN rules, another VPN, battery management or network changes interrupt access, the app says **Sync paused · changes saved on this phone** and keeps working offline. No port forwarding or public tunnel instruction.
3. Pull a checked snapshot of switched-on parts into a bounded temporary store; verify household ID, version, digest, links and cursor, then atomically replace the accepted copy without deleting the phone's unsent outbox. Later deltas apply in order. Keep a protected local database and a separate durable outbox. OS backups, device encryption and lost-phone behavior need a clear product policy. A PIN/biometric gate can protect app opening but cannot replace disk protection or main's revocation.
4. Apply decision 0089's field travel rule before any record enters the phone: medical safety details travel and stay behind Show; access instructions, Home layout codes and vehicle registration remain on their origin computer. A phone-typed local-only field remains on that phone and never enters push, log, error or Review. Its placeholder must never be treated as a clear operation. Preserve the person's original local value across pull, restore and app update.
5. Push the phone's saved operations with stable IDs, base revision and one-use operation IDs. Main stages each row on Review; a network acknowledgement means **sent for review**, not accepted. The phone shows waiting, accepted, rejected and needs-rework separately. Retrying must not create duplicate Stock movements. A revocation blocks future exchange but cannot erase the phone's already downloaded data. Do not use push notifications containing household facts or secret values.

The phone app should not expose a local server, desktop Settings, helper API, main-only Review approval or database file-sharing surface. It needs a reviewed migration path for its local store and a way to export/recover its own unsent changes if an update fails. Long-offline members require a fresh snapshot and separate outbox reconciliation, as in decision 0089.

## First phone screens and exact initial scope

| Screen | First version behavior | Guardrail |
|---|---|---|
| Needs attention | Compact list of enabled-part warnings from the last accepted pull, plus **On this phone** edits waiting to send or waiting on main. Show accepted-main revision and last pull time; stale state gets **May have changed on main**. | No readiness claim based on an unaccepted phone edit. Medical details remain hidden until Show. |
| Stock in / Stock out | Find an existing item and batch, show full place path, enter amount/unit and a short reason, then **Save on this phone**. Offer a clear choice when a batch is missing; do not invent expiry or place. | Offline save writes one durable operation. Repeated tap does not duplicate it. Stock out cannot make the locally known batch negative; main validates again at Review. |
| Count this batch | Show item, batch, place, last accepted count and **I counted** amount. Before save, explain **Main will compare this count with any newer movements**. | Send observed amount/base, not a precomputed correction. If main changed, person at main resolves the stale count; phone never silently adjusts accepted stock. |
| Review | On a member, title **Changes waiting on main**: rows grouped as saved here, sending, waiting for main, accepted, rejected or needs rework. Open a row for main's explanation and retry/edit options. | No Accept/Reject buttons on phone: decision 0089 assigns approval to main. A phone does not show other members' staged private details. |
| Pairing and Sync status | Device name, main identity, chosen private-network setup, last pull, unsent count, paused reason and **Turn off this phone** instructions. | Never reveal a member key after pairing; remind that copied records can remain on a lost phone. |

At 320px, buttons need touch-sized targets, labels and error summaries, visible focus and screen-reader order. Offline and waiting status must use words as well as color. A compact phone view may show fewer fields, but it must not change the sync record or silently discard hidden fields.

## Store rules and running costs

Publishing a native or cross-platform packaged iOS app through the App Store requires Apple Developer Program membership, signing, privacy disclosures and App Review. Publishing through Google Play requires a Play Console developer account, app signing/policy declarations and current target-API compliance. Both stores can reject an app that misstates data collection, breaks, or lacks requested account/privacy information. Even if Dashboard has no central server, medical safety details and household records live on devices; the store privacy answers must describe the app's actual handling and any diagnostics. The member app should not claim end-to-end secrecy or a vault. A private-network vendor may have its own household plan costs; self-run WireGuard requires setup and maintenance. Do not assume a free hosted service for the product promise.

Cost drivers are two store accounts (Apple membership is recurring; Google Play registration is a one-time fee, subject to country and tax), Mac build/signing hardware or runner for iOS, two release pipelines, real-device test time, mobile secure-storage and database dependencies, accessibility, OS updates, support for VPN setup and lost-phone recovery. Verify current checkout amounts at release rather than hard-coding them into household instructions. A PWA can avoid store accounts, but does not remove the engineering and support costs of safe offline data and private-network access. The cross-platform option reduces duplicate UI work but still has two signing and review paths.

## Acceptance for a first phone prototype

1. On current Android and iOS devices, pair against invented main through each supported private-network adapter; wrong main fingerprint, expired QR, helper key and revoked member all fail before data transfer. Switch adapters without changing record IDs or duplicating an operation.
2. Pull an invented household with Stock, People, Home layout and Vehicles. Search app database, network capture, logs, diagnostics and OS backup for local-only sentinels. Medical allergy/care details travel behind Show; access details and registration do not. A phone-typed access detail never appears on main.
3. Airplane mode: Stock in, Stock out and Count this batch save locally, survive forced quit/restart and show unsent status. Reconnect, send twice, confirm one Review request per operation and zero live main changes before approval.
4. Main accepts one row, rejects another and changes a batch before a count arrives. Phone displays each outcome after pull; rejected edit remains recoverable and stale count awaits a human decision on main. Test last-pull age and forced clock skew.
5. Fill and nearly fill the phone storage; interrupt snapshot, delta, app update and VPN connection. Old accepted copy and outbox survive or a clear recovery path appears. No secret enters notifications or crash logs.
6. Test 320px layout, large text, VoiceOver and TalkBack, keyboard/switch navigation, dark mode and a full emergency sheet. A phone member cannot approve Review, restore main or reach the helper API through the sync path.
7. Review App Store and Play privacy declarations against the actual build, including VPN dependency, diagnostics, backups and medical data. Test a clean install from the intended distribution channel, not just a developer build.
