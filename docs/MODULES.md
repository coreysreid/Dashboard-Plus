# Make a module of your own

A module is a small folder of text files that tells Dashboard Plus what you want to keep track of. You can write one yourself or ask a helper to draft it. Your household's records stay in its own data folder. The [vegetable garden example](../examples/garden/INDEX.md) is a complete starting point; it lives under `examples/`, so it is not switched on for every household.

1. **Choose the records you need.** Write down the things you want to remember and how they connect. The garden has beds, crops, plantings, harvests and jobs. A planting points to one bed and one crop; a harvest points to a planting. Start small. You can add a field later with another migration.
2. **Copy the example folder.** Give the copy a short lower-case name such as `orchard`. Keep it under `examples/` while you experiment. Change `module.toml`'s `name`, `title`, `description` and `version`. The name must match the folder. `kind = "declarative"` means the module is made from files alone; it runs no custom Python. Leave `core_api = "1"` unless the core contract changes. List other modules in `requires` only if needed, and leave `outbound_hosts` empty for an offline module.
3. **Describe the records in `tables.toml`.** Each `[tables.name]` is a kind of record. Give it a title and columns. For each column, choose a type such as `text`, `longtext`, `date`, `integer`, `decimal`, `boolean`, `choice` or `link`. Use `required = true` only when a blank value would make the record useless. A link's `to` names a table in this module. For example, a garden harvest links to a planting. The core supplies IDs and history fields, so do not declare them yourself.
4. **Make the forms readable in `labels.toml`.** For every table, list the columns to show in `form` and `list`. Add friendly labels or help where the field name alone is unclear. The garden calls `amount` “How much”. This file changes the words and layout, not the data itself.
5. **Add an optional printed page in `sheets.toml`.** A sheet has a title and sections. Each section names a table and the columns to print. The garden plan lists beds, plantings and unfinished jobs. Include sensitive fields only when the printed copy truly needs them; printed pages can be left where others see them.
6. **Generate the database change.** From the project root, run `python tools/make_migration.py garden --modules-dir examples` for the garden, substituting your folder name for `garden`. The tool writes a numbered SQL file in `migrations/`. Check that the generated file matches the tables you meant to create. Once a migration has been used with real data, never edit it; change `tables.toml` and generate the next migration instead.
7. **Try it with made-up records.** Run `PYTHONPATH=src python -m unittest discover -s tests` and use `tests/test_example_garden.py` as a model for a test. It loads the module, prepares a temporary database and saves a bed, crop, planting, harvest and job. Test with synthetic details only. A malformed module reports problems when it loads; fix those before using it with household records.
8. **Choose whether to install it.** To make the module available to a household, copy its finished folder into that installation's `modules/` directory and open Dashboard Plus with that modules directory. Keep your draft and private records outside the public repository. Sharing the module files does not share your household database.

The [design](DESIGN.md#6-modules) explains the full file contract, including optional watch views and how module versions work. A helper should read that contract and the project's [contribution rules](../AGENTS.md) before proposing a public module. Keep examples and tests free of real names, addresses, phone numbers and data.
