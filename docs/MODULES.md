# Make a module of your own

A module is a small folder of text files that tells Dashboard Plus what you want to keep track of. You can write one yourself or ask a helper to draft it. Your household's records stay in its own data folder. The [vegetable garden example](../examples/garden/INDEX.md) is a complete starting point; it lives under `examples/`, so it is not switched on for every household.

1. **Choose the records you need.** Write down the things you want to remember and how they connect. The garden has beds, crops, plantings, harvests and jobs. A planting points to one bed and one crop; a harvest points to a planting. Start small. You can add a field later with another migration.
2. **Copy the example folder.** Give the copy a short lower-case name such as `orchard`. Keep it under `examples/` while you experiment. Change `module.toml`'s `name`, `title`, `description` and `version`. The name must match the folder. `kind = "declarative"` means the module is made from files alone; it runs no custom Python. Leave `core_api = "1"` unless the core contract changes. List other modules in `requires` only if needed. If a link is useful but the record makes sense without it, list that module in `optional_requires` instead: your module then works while it is off, the link is optional and kept as saved, and you can give the household's words for it in labels.toml (`columns.<name>.optional`, decision 0115). Leave `outbound_hosts` empty for an offline module.
3. **Describe the records in `tables.toml`.** Each `[tables.name]` is a kind of record. Give it a title and columns. For each column, choose a type such as `text`, `longtext`, `date`, `integer`, `decimal`, `boolean`, `choice` or `link`. Use `required = true` only when a blank value would make the record useless. A link's `to` names a table in this module. For example, a garden harvest links to a planting. The core supplies IDs and history fields, so do not declare them yourself. A private column (`sensitive = true`) should also say whether it may one day travel to the household's other computers: `travels = "never"` keeps it on the computer where it was typed, and one that does not say is kept there too until someone decides (decision 0100). These rules are where each household starts: it can change them on Settings, What your other computers get (decision 0140). A table can say `travels = "never"` to start the whole list kept on this computer, and a column with `travels = "never"` can add `travels_fixed = "<why, in a sentence>"` for something like a code that must never be shared at all.
4. **Make the forms readable in `labels.toml`.** For every table, list the columns to show in `form` and `list`. Add friendly labels or help where the field name alone is unclear. The garden calls `amount` “How much”. This file changes the words and layout, not the data itself. On the home page your module gets one card: its first table is shown large and the others as a line of links. To choose differently, add `home = "main"` to the table people open most (more than one is allowed) or `home = "more"` to one that should be a link.
5. **Add an optional printed page in `sheets.toml`.** A sheet has a title and sections. Each section names a table and the columns to print. The garden plan lists beds, plantings and unfinished jobs. Include sensitive fields only when the printed copy truly needs them; printed pages can be left where others see them.
6. **Generate the database change.** From the project root, run `python tools/make_migration.py garden --modules-dir examples` for the garden, substituting your folder name for `garden`. The tool writes a numbered SQL file in `migrations/`. Check that the generated file matches the tables you meant to create. Once a migration has been used with real data, never edit it; change `tables.toml` and generate the next migration instead.
7. **Try it with made-up records.** Run `PYTHONPATH=src python -m unittest discover -s tests` and use `tests/test_example_garden.py` as a model for a test. It loads the module, prepares a temporary database and saves a bed, crop, planting, harvest and job. Test with synthetic details only. A malformed module reports problems when it loads; fix those before using it with household records.
8. **Choose whether to install it.** To make the module available to a household, copy its finished folder into that installation's `modules/` directory and open Dashboard Plus with that modules directory. Keep your draft and private records outside the public repository. Sharing the module files does not share your household database.

**Entries you count by the day.** If each record is one timed event for one subject, such as one feeding for one pet, a table can add a `daily` section and get honest daily totals, a day page, a Home line and a dated sheet without new screens. `modules/pet_feeding/tables.toml` is the example: `when` names a required date-and-time column, `per` the required link to the subject, `amount` and `unit` an optional amount with its unit (they must be filled in together, and totals only ever add the same unit), plus the words the pages use (`entry`, `what`, `verb`, `add`, `sheet`, `caveat`). An optional `repeat = { minutes = 30, same = ["food", "amount", "unit"] }` makes Review mark a helper's suggestion that looks like one already recorded. Days follow the household's own time zone, and a day with no entry is never read as something missed (decision 0110).

**Private history and links that must fit.** `modules/medicine_doses/tables.toml` adds three things (decision 0120). `private = true` on a table makes every record private history: it never appears on Home, a sheet, the spreadsheet export or to a helper, and the table must also say `suggestions = false`. A link column's `link_rule = { where = { kind = "medication" }, same = { person = "recipient" }, shows = "detail" }` limits what may be chosen: the linked record must have those choices and the same person as this record, checked on every save (and the linked record cannot be changed so that it no longer fits); `shows` names its private column a person may Show from the form. In `daily`, `group = "medication"` keeps each linked record's totals apart, and `repeat` may add `form` (a question asked before saving) and `keep` (the button that saves anyway) for a table nobody suggests into.

**Bars over time.** A table with dated or timed records can add `[[tables.<name>.bars]]` sections and get bars per day, week or month on each subject's page and at `/bars/<table>/<key>`: `measure = "count"` counts entries (optionally only those with `where` choices, such as Routines' `outcome = "done"`), and `measure = "sum"` adds one number column in one unit at a time, as Pet feeding does for food put out. `group` gives each linked record its own bars; a private table may only count, and its groups appear only after Show, as Medicine doses does. Add `history = true` to count each day a "last done" date says it was done, as Garden's Jobs done per month does (decision 0129). The design's section 5.13 shows every setting (decision 0124). Leaving out `per` gives one chart of the whole list, `group = "item.category"` gives each choice of the linked record its own bars, and a private or money `amount` is counted until a pressed Show and added up after it, as Household stock's Spent per month does (decision 0128).

**A confirmed purchase price.** A table of bought things can declare `[tables.<name>.price]`: the price a person typed, whether it is the total or the price for each one, the worked-out line total and the currency, all private columns that stay on this computer (`travels = "never"`), and `only` saying which records may carry a price. The design's section 5.13a shows every setting (decision 0128).

**Money back.** A table of refunds can declare `[tables.<name>.refund]`: the Stock in it is for (`of`), the day (`when`), which of that table's columns hold its line total and currency (`paid`, `currency_of`), the refunded amount, its currency and the "more than was paid" tick (`amount`, `currency`, `confirm`, all private and `travels = "never"`). A bars chart can name it with `refunds = "<table>"` to say money back beside each bar after Show (decision 0133, section 5.13b).

**One timeline on a record's page.** A table with dated or timed records can add a `[tables.<name>.timeline]` section to put its entries on the page of the record it links to, under **What happened, newest first**: `when`, `per` (or one link further inside the module, such as Pets' `per = "treatment.pet"`), `entry`, optional `words` with `{column}` names (never a private column), one of four fixed `look`s, `summarise = "day"` for one line a day (Pet feeding; required for a private table, as Medicine doses does) and `change` for the change since the entry before in a column with its own unit (Pets' weigh-ins), or with `change_unit` naming the choice column that gives each entry's unit, compared only between entries in the same unit (the Vehicle running log's readings). `per` may go through one link into a module this one requires (estimates: `per = "service.vehicle"`). The design's section 5.14 shows every setting (decisions 0126 and 0130).

**Bring in earlier entries.** A dated log can add `[tables.<name>.bring_in]` with `when` (its required date or date-and-time column) and `per` (the required link each entry is about), and optional `entry` words. Its list page then offers **Bring in earlier entries**: the household chooses their own CSV, matches its columns, sees every row with plain problems, picks an existing record for any name that matches nothing (nothing is ever created), and adds them all at once with one **Undo**. A private list asks for **Show** first. A list that changes amounts, joins records, moves reminders or keeps prices can't use it. Pets' weigh-ins, Pet feeding, Medicine doses and the Vehicle running log's readings do. The design's section 5.15 has the details (decision 0137).

A few optional extras ask nothing new of the database: a gentle check before saving (an odometer reading lower than the last one asks **Go back** or **Save as entered**), a table's records listed on the page of the record they link to (a service's quotes), and a dots chart of one subject's readings. A due date can use other words for some rows (`what_when`, such as "bill check" for bills), and a table can offer to take over another module's reminders one record at a time (`takes_over`, as Bills does for Vehicle insurance), only when the household chooses, never by name, with Transfer back (decision 0117). The Vehicle running log module uses all three; the design's section 5.10 shows how (decision 0111). A month `calendar` also asks nothing new of the database: on a log table it names the date and the record each entry belongs to (`per`, like Work done's job, decision 0119); on a table whose records carry their own due date, such as Garden jobs, Documents, Home layout's alarms or Things lent out, leave out `per` and write `due = true`, and each record's date and its Mark done presses show on Things to do's Calendar tab, labelled with your module's title (decision 0122). If that table keeps one "last done" date, such as a service's `last_done`, add `history = true` and every earlier date it was moved on from shows too, read from the record's own history; a date typed back, or changed or cleared the same day it was typed, never counts (decision 0129). A household can take any such earlier day off with **Not a done day**, with Undo; your module declares nothing more for it (decision 0132). The design's section 5.12 shows both.

The [design](DESIGN.md#6-modules) explains the full file contract, including optional watch views and how module versions work. A helper should read that contract and the project's [contribution rules](../AGENTS.md) before proposing a public module. Keep examples and tests free of real names, addresses, phone numbers and data.
