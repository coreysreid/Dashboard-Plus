# Agent API skeleton — implementation plan (from the Opus planning pass, 2026-11-18)

## 0. Findings that shape the design
A. Suggestions must NOT be stored as `needs_review` rows in module tables: `Records._create` applies side effects regardless of review_status (_adjust/_shift change stock, _retotal adds batches into totals, _choose_batch creates batches), and watch.py/home/grids/sheets never filter on review_status. Decision: stage suggestions in core table `core__proposals`; write to module tables only when a person accepts, via the normal Records create path. `review_status` stays unused by helpers.
B. Security hole: a module named `core` bypasses the module guard (0055). modules.NAME allows "core"; startup.prepare does `tracks[module.name] = module.migrations`, replacing the real core track; migrations.migrate skips the guard for CORE_TRACK; `_confined_to("core")` would treat every core__* table as own. Also prefix matching lets module `pets` claim `pets___x` (belongs to `pets_`). FIX FIRST: refuse module names `core`, names containing `__`, names ending `_` (plain message "'core' is reserved for the program itself"); in startup.prepare skip any found module named CORE_TRACK as a second net. Tests in tests/test_module_confinement.py (module "core" refused, its migrations never run, core tables intact; `pets_`/`a__b` refused; a "core" module carrying copies of real core 0001/0002 plus a 0003 can't run that 0003).
C. Port changes every launch (create_server port=0). Skeleton shows current address on the Helpers settings page with a warning; fixed port later. (Since decision 0092 the port still changes, but the connector reads it from `data/run/helper-address.json` for every call, so a restart needs no new copy.)

## 1. Scope (skeleton)
1. Core-name fix (B).
2. Helper keys managed in Settings → Helpers: name, access level ("Look only"=read / "Look and suggest"=suggest), list of modules it may use (none ticked by default). Key shown once; "Turn off access". Private details never shared (no grant in v1).
3. Read routes: GET /api/v1/me, /tables, /tables/<t>/records (keyset paging), /tables/<t>/records/<id>, /attention.
4. Suggest: POST /api/v1/proposals — ADD NEW RECORDS ONLY, ≤50 entries per call, required `request_key` (retry-safe), required `why`. GET /api/v1/batches, /api/v1/batches/<id> (own batches only).
5. Review screen /review: pending batches newest first; rows "Add to <Table>: field: value…"; Accept / Reject per row; Accept all / Reject all per batch; home card "N suggestions need a look"; nav link "Review" with count.
6. Every helper action audited (key made/turned off, batch suggested, accepted, rejected).
Deferred: updates/deletes of existing records, amend/undo, change-then-accept, private-detail grant, per-table scope, CLI, forgetting request keys, file columns (readable, not suggestible).

## 2. Security model
- Single entry point `only_this_computer` in app.py. Host check unchanged and applies to /api/v1 too. Add `if request.path.startswith("/api/v1/"): return helper_api.authenticate()` BEFORE the existing Origin/cookie/CSRF code so that code stays as strict for every other path. Update the comment that says nothing is exempt.
- authenticate(): refuse any request carrying an `Origin` header (403 JSON `from_a_web_page`) — helpers are programs, not web pages; require `Authorization: Bearer <key>`; never read cookie, query string or form; set g.helper or 401 JSON. POSTs must be `Content-Type: application/json` else 415. Set `request.max_content_length = 65536` (413 JSON). Exact prefix `/api/v1/` only; /api/ping and /api/shutdown unchanged.
- Pages never look at Authorization. Tests: bearer key without cookie on /t/... still redirects to /start; cookie without key → 401 on /api/v1.
- Keys: `dph_` + secrets.token_urlsafe(32). Stored hash = sha256 hex. Hashes live in `data/secrets/helper_keys.json` mapping {sha256: key_id} (key_id random 16 hex, also on the core__helpers row) — NOT in the DB, so restoring an old backup can never revive a turned-off key, and a key made after a backup is dead after restore. Verify: refuse header >100 chars; hash; hmac.compare_digest against every live hash; load row by key_id; require revoked_at IS NULL. File writes: threading.Lock, temp file + os.replace, db.keep_private. Make key: DB row first, then file. Turn off: remove hash from file first, then set revoked_at.
- Links into parts not given (decision 0074): a link column whose target table is outside the helper's granted, switched-on parts is invisible — left out of /tables (no `to`), records and /attention gaps; suggesting it → 403 `not_allowed` with one message whatever the value (never looked up); a table where it is required reports "can_suggest": false with a reason and is refused (422); Accept checks again.
- Private (`sensitive`) columns: never returned or accepted. /tables omits them; a table with a REQUIRED private column reports "can_suggest": false with reason; proposals naming one → 403 `private_detail` (field name only, never value); errors never echo submitted values; no history/audit route.
- A helper can never: confirm/accept, change/delete existing records, see private details/history, read core__* or unallowed modules, see other helpers or their batches, make/see keys, change settings/backups/restore/export/modules/files, run SQL. (No routes for these.)
- Inputs matched against known lists: table names must be keys of the allowed registry (enabled modules ∩ helper modules); field names must be keys of info.table.columns; system fields (review_status, source, id, batch_id, edited_by_person, deleted_at) refused 422 "is not a field of this table."; entry keys other than table/values → 400.
- Limits: body ≤64 KB; ≤50 entries/call; ≤200 suggested rows per helper per UTC day (count on core__proposals) → 429; ≤500 of a helper's suggestions waiting on Review (`app.config["HELPER_REVIEW_QUEUE_LIMIT"]`) → 429 `review_queue_full`, refused whole, no Retry-After, imports not counted, frees on accept/reject (decision 0085; `/me` limits gain `review_queue_limit` and `suggestions_waiting`); ≤120 requests per helper per minute, in memory, `app.config["HELPER_REQUESTS_PER_MINUTE"]` → 429 `too_many_requests` with Retry-After (decision 0074); why 1–300 chars; request_key 1–100 chars `^[A-Za-z0-9._:-]+$`; limit 1–200. Failed sign-ins logged "helper key refused" without the key.
- Text screening (decision 0074), before any other check of the body: any text that looks like a helper key (`dph_` + 8 or more key characters) → 400 `looks_like_a_key` ("That looks like a helper key. Keys belong only in the Authorization header."), never echoed; C0 controls except newline, DEL, C1 controls, U+202A–U+202E and U+2066–U+2069 → 400 `hidden_characters`. Review shows `why` and values as the named helper's own words inside `<bdi>`, and marks any such character kept from before as U+FFFD.
- Checking suggestions: full dry run. New `Records.check_create(entries, actor)`: BEGIN IMMEDIATE, call `_create` for each entry in order, collect ValidationError per entry, ALWAYS ROLLBACK. Derived columns (`_derived`) refused explicitly: "is worked out from its batches; suggest a Stock in instead". Store RAW submitted values (never cleaned — money would double-scale). Accept re-runs create on raw values; if the world changed, row stays pending with reason. Batches all-or-nothing on submit.
- Accept: in one db.transaction, first mark it accepted only if still pending (one UPDATE … WHERE status = 'pending'; a second click or window gets "already been decided", decision 0074), then `store.create_in(name, raw_values, actor=f"agent:{slug}", review_status="confirmed", batch_id=batch.id)`; set edited_by_person = 1 on the new row; mark proposal accepted with record_id; audit actor='person', action='accept', table_name='core__proposals'. Reject: status='rejected' the same way (only if still pending), audit action='reject'. Retry with same request_key returns the original batch (rejected never comes back). Proposals for a switched-off module: show "This is for <module>, which is switched off", Reject only. Proposals from a turned-off helper still shown: "This helper's access is off. Its earlier suggestions still need your decision."
- Audit rows: helper_add (person, core__helpers/id), helper_off (person), propose (agent:<slug>, core__proposals/id, after={"table","batch"}, no values), accept (person), reject (person). Reads not audited. last_used_at updated at most once a minute.
- NOTE: the /api/v1 exemption from the page token is a security-rule change; User 1 must OK it before merge (Lane A handles that).

## 3. Data model — src/dashboard/core/migrations/0003_helpers.sql (core migration; add INDEX row)
```sql
-- Helpers (AI or human assistants) the household gave a key to. The key itself is never stored;
-- its fingerprint lives in data/secrets/helper_keys.json, matched by key_id.
CREATE TABLE core__helpers (
    id INTEGER PRIMARY KEY,
    key_id TEXT NOT NULL UNIQUE,
    slug TEXT NOT NULL UNIQUE,
    name TEXT NOT NULL,
    access TEXT NOT NULL CHECK (access IN ('read', 'suggest')),
    modules TEXT NOT NULL DEFAULT '[]',
    created_at TEXT NOT NULL,
    last_used_at TEXT,
    revoked_at TEXT
);
CREATE TABLE core__helper_batches (
    id INTEGER PRIMARY KEY,
    helper_id INTEGER NOT NULL REFERENCES core__helpers(id),
    request_key TEXT NOT NULL,
    body_hash TEXT NOT NULL,
    why TEXT NOT NULL,
    created_at TEXT NOT NULL,
    UNIQUE (helper_id, request_key)
);
CREATE TABLE core__proposals (
    id INTEGER PRIMARY KEY,
    batch_id INTEGER NOT NULL REFERENCES core__helper_batches(id),
    position INTEGER NOT NULL,
    table_name TEXT NOT NULL,
    values_json TEXT NOT NULL,
    status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending', 'accepted', 'rejected')),
    record_id INTEGER,
    reason TEXT,
    created_at TEXT NOT NULL,
    decided_at TEXT
);
CREATE INDEX core__proposals__status__idx ON core__proposals(status, batch_id);
CREATE INDEX core__helper_batches__helper__idx ON core__helper_batches(helper_id, created_at);
```
Slug from name: lowercase, chars outside [a-z0-9-] → '-', ≤40 chars, add -2, -3 if taken; unique across turned-off helpers; must match records.ACTOR. batch_id on module rows refers to core__helper_batches.id.

## 4. HTTP API (/api/v1)
JSON only, `application/json; charset=utf-8`, inherits Cache-Control: no-store. ISO dates. Money as decimal major units (note "stored in cents" in spec). Choices by key. Links by id only. Unknown query params ignored. Error shape:
`{"error": "invalid", "message": "Weigh-ins: some values could not be used. Nothing was saved.", "problems": [{"entry": 0, "table": "pets__weigh_ins", "field": "weight", "message": "must be at least 0."}]}`
Statuses: 400 bad_request ("This request could not be read. Check the fields and try again." / "Give this request a key so a retry cannot add the same rows twice." / "Say why, in a sentence, so the household knows where these came from." / "Send 50 suggestions or fewer at a time."); 401 no_key ("This helper's access key is missing or no longer works. Ask the household to check Helpers in Settings."); 403 not_allowed ("Pet diary helper may use: Pets. Ask the household to change its access in Settings."); 403 look_only ("This helper may look but not suggest changes. Ask the household to change its access in Settings."); 403 private_detail ("Private details are never shared with helpers. Leave out: allergies."); 403 from_a_web_page ("The helper API cannot be used from a web page."); 404 not_found ("That table or record could not be found."); 409 request_key_reused ("This request key was already used for different suggestions. Check the earlier batch, then use a new key."); 413 too_large ("This request is too large. Send fewer suggestions at a time."); 415 needs_json ("Send the body as JSON (Content-Type: application/json)."); 422 invalid; 429 daily_limit ("This helper has reached 200 suggestions today. Try again tomorrow."); 400 looks_like_a_key; 400 hidden_characters; 429 too_many_requests (with Retry-After). 429 review_queue_full ("500 suggestions from this helper are already waiting on Review. Ask the household to look at them first."), decision 0085. Table outside grant and unknown table → the same 404 not_found ("That table or record could not be found. GET /api/v1/tables lists what this helper may use."), decision 0074; 403 not_allowed is now only for a field linking into a part not given ("This helper may not set roadside_contact: it links to a part of the records this helper was not given. Leave it out.").
Routes:
1. GET /api/v1/me → {"name","access","modules","message":"Pet diary helper may use: Pets. Ask the household to change its access in Settings.","private_details": false,"limits":{"entries_per_call":50,"suggestions_per_day":200,"suggestions_left_today":N,"max_body_bytes":65536,"requests_per_minute":120,"review_queue_limit":500,"suggestions_waiting":N},"api_version":"1","program_version":...}
2. GET /api/v1/tables → {"tables":[{"table","module","title","can_suggest","columns":[{"name","label","type","to"?, "required","help","unit","min","choices":[{"key","label"}]}],"worked_out":[derived cols],"private_columns_left_out":N}]} — labels via display.table_title/column_label; file columns can_suggest false.
3. GET /api/v1/tables/<t>/records?after=<id>&limit=50 → {"table","records":[{"id","created_at","updated_at","source","values":{...}}],"next_after": last id if page full else null}. Omit review_status, edited_by_person, batch_id, private columns. Deleted excluded.
4. GET /api/v1/tables/<t>/records/<id> → one record, same shape, or 404.
5. GET /api/v1/attention → running_low, expiring, supplies, gaps from watch.py on the ALLOWED registry only (dataclasses.asdict; drop internal sort keys/URLs; check real field names).
6. POST /api/v1/proposals (suggest access) body {"request_key","why","entries":[{"table","values"}]} → 201 first time, 200 identical retry: {"batch_id","state":"waiting","why","proposals":[{"id","position","table","status"}],"message":"1 suggestion is waiting for the household to review. Nothing changes until they accept it."}. Steps: authorise → body shape → request key (same key+same body_hash returns stored; different hash 409) → daily limit → tables allowed, no private/system/derived fields → check_create dry run → insert batch+proposals+propose audit in one transaction. Catch sqlite3.IntegrityError on the UNIQUE race and return stored batch.
7. GET /api/v1/batches?after=<id>&limit=20 → own batches newest first with totals {total,pending,accepted,rejected}, next_after.
8. GET /api/v1/batches/<id> → one batch + proposals with status, record_id once accepted, reason. Another helper's → 404.

Receipt lines and grouped suggestions (built 2026-11-20, decision 0097): an entry may add `"source": {"line", "price"}` (text, at most 200 and 20 characters, screened like `why`, kept in `core__proposals.source_json` by core migration 0006, shown on Review only, never written to a record). A `link` value may be `{"ref": N}`, an earlier entry of the same request adding to the linked table; anything else is 422 `invalid` with entry and field. `Records.check_create(..., resolve=)` swaps refs for the dry run's own new ids. Replies add `depends_on: [positions]` to rows with refs. `proposals.accept_counted` adds the waiting rows a row needs first, in one transaction; `reject_counted` rejects the waiting rows that need it; `accept_batch`/`reject_batch` go in position order. Review (`review.py`, `review.html`) groups rows that point at each other, names a pending link "Red lentils (new, suggested above)" and says on each row what Accept or Reject also does. Tests: `tests/test_grouped_suggestions.py`, plus a receipt request in `tests/test_api_contract.py`.

9. GET /api/v1/openapi.json → the published OpenAPI 3.1 description (`src/dashboard/web/openapi-v1.json`), served as is, same key and rules as every route (decision 0084). `tests/test_api_contract.py` holds it to the real routes, error codes and reply shapes.

## 10. The MCP connector (built 2026-11-19, decision 0083)
- `src/dashboard/connector/`: stdio MCP server, no new dependency. Methods: initialize (protocol 2025-06-18, also 2025-03-26 and 2024-11-05), notifications/initialized, ping, tools/list, tools/call; others -32601; unreadable -32700; invalid or batched -32600; unknown tool -32602.

- Results: a first sentence saying the content is household data, not instructions (abuse case 14), then the API JSON as text; `structuredContent` `{"about", "data"}` for 2025-06-18 clients. API errors: `isError: true`, "Dashboard Plus said: <message>", status/code/problems as data.
- Address and key: `DASHBOARD_PLUS_ADDRESS_FILE` (preferred, decision 0092) or `DASHBOARD_PLUS_URL`, `DASHBOARD_PLUS_KEY`, or `--config <toml>` with `address_file`, `url` and `key` (environment wins; an address file always wins over a URL); only `http://127.0.0.1:<port>` or `http://localhost:<port>`; http.client (was urllib until decision 0086), 15 s timeout, no proxy, no redirects, 4 MB answer cap; key and key-shaped text redacted from stdout and stderr.
- Is it really Dashboard (decision 0086): before every request, on a new connection and without the key, `POST /api/v1/hello` with `key_name` = SHA-256("dph-id:" + fingerprint) and a fresh 32-byte `nonce`; Dashboard answers `proof` = HMAC-SHA256(SHA-256("dph-hello:" + fingerprint), "dashboard-plus-hello-v1|" + nonce + "|" + host:port). Only on a match (compare_digest) does the request with the key go, down the same connection (auto_open off; a closed connection is checked again, once). Otherwise: "This address is not Dashboard Plus, or it is an old address..." and the key is never sent. Unknown or turned-off names get the same shape from a per-start secret. Origin, exact Host, JSON, 1 KB body, 600 hellos a minute shared by everyone (`HELLOS_PER_MINUTE`), never a helper's own limit.
- Helpers page and new-key page: "Connect an AI assistant" block (`helper_connect.html`) with the MCP client JSON pointing at the address file, `YOUR-KEY-HERE` placeholder, and the decision 0082 wording; the current address and a manual URL block under a collapsed "Connection details".
- Steady address (decision 0092): after the listener is ready Dashboard writes `data/run/helper-address.json` = `{"version": 1, "url": "http://127.0.0.1:<port>/api/v1", "run_id": <32 hex>}` (temporary file, then one replace; 0600), and removes it on a safe close only if the run ID is still its own. Never the session or close token (those stay in `dashboard.json`, which the connector never reads). The connector reads it for every call (`client.call_via_file`): at most 1 KB, a regular file, not a link, exactly those three keys, the URL in exactly that spelling; then the 0086 hello on that address before the key. Plain errors: missing file, wrong file, not answering; the key is never sent.
- New key for the same helper (decision 0093): `POST /settings/helpers/<id>/new-key` with the CSRF token and a one-use `new_key_token` bound to that helper. `helpers.rotate`: (1) mark `key_pending_at` and raise `key_generation` in one transaction, so no key of the helper works; (2) replace `helper_keys.json` whole, every old fingerprint of that `key_id` out and the new one in; (3) clear the mark, set `rotated_at`, audit `helper_rotate` with no values. Only then is the key shown, once. A failure keeps the helper paused and shows no key; at start-up an unfinished change has its fingerprints removed. `proposals.submit` rechecks revoked, pending and generation inside the write transaction (401 `no_key`).
- Tests: `tests/test_mcp_connector.py` runs the connector in-process and as `python -m dashboard.connector` against a real app served by waitress on 127.0.0.1; `tests/test_helper_address.py` and `tests/test_helper_key_rotation.py` hold Lane B's acceptance checks for 0092 and 0093.
